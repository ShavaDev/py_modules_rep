Компиляция SQL-запроса — это процесс превращения текстовой команды в эффективный алгоритм действий для процессора. Это похоже на то, как повар читает рецепт (текст), переводит его в план действий (сначала режем, потом жарим) и выдает готовое блюдо.

В большинстве современных СУБД (PostgreSQL, Oracle, SQL Server, DB2) этот процесс проходит через 5–6 строгих этапов.

1. Парсинг (Parsing)
На этом этапе база данных проверяет, правильно ли написан запрос с точки зрения грамматики языка.

Синтаксический анализ: Проверка запятых, скобок, правильности написания команд (SELECT, FROM, WHERE). Если ты напишешь SELEC вместо SELECT, база выдаст ошибку здесь.

Семантический анализ: База проверяет, существуют ли таблицы и колонки, к которым ты обращаешься. Есть ли у тебя права доступа к ним?

Результат: Создается логическое дерево запроса (Parse Tree).

2. Трансляция и нормализация (Rewriting / Algebrizer)
База пытается упростить твой запрос, не меняя его сути.

Например, если ты написал WHERE 1=1 AND price > 100, база выкинет 1=1, так как это лишнее действие.

Раскрываются представления (VIEW). Вместо имени вьюхи подставляется её реальный код.

Результат: Нормализованное дерево, готовое к расчетам.

3. Оптимизация (Optimization) — «Сердце» процесса
Это самый сложный этап. База данных решает, как именно она будет доставать данные. У одного запроса могут быть сотни вариантов исполнения.

Статистика: Оптимизатор смотрит на данные: сколько строк в таблице? Насколько уникальны значения в колонке?

Выбор индексов: Использовать индекс или сканировать всю таблицу целиком?

Выбор алгоритмов Join: Как соединять таблицы? Методом Nested Loops (цикл в цикле), Hash Join или Merge Join?

Стоимостная модель (Cost-based Optimizer): Каждому варианту (плану) присваивается «стоимость» (в единицах процессора и дискового ввода-вывода). Выбирается план с наименьшей стоимостью.

Результат: План выполнения (Execution Plan).

4. Генерация кода (Code Generation)
Выбранный план превращается в понятный для машины код (байт-код или инструкции), который будет выполняться движком базы данных.

Разные случаи компиляции:
А. Жесткая компиляция (Hard Parse)
Происходит, когда база видит этот запрос впервые. Она проходит все этапы от парсинга до генерации плана. Это «дорогое» удовольствие, которое нагружает процессор.

Б. Мягкая компиляция (Soft Parse)
Перед тем как компилировать, база заглядывает в кэш планов (Plan Cache).

Если ты уже выполнял точно такой же запрос секунду назад, база просто берет готовый план из памяти и сразу переходит к исполнению.

Важно: Если в запросе меняется хоть один символ (даже лишний пробел или регистр), база может посчитать его новым и запустить Hard Parse.

В. Использование Bind Variables (Связанные переменные)
Это то, что отличает профи от новичка.

Плохо: SELECT * FROM Users WHERE id = 1, затем SELECT * FROM Users WHERE id = 2. Это два разных запроса (два Hard Parse).

Хорошо: SELECT * FROM Users WHERE id = ?. База компилирует запрос один раз, а потом просто подставляет разные значения id. Это всегда Soft Parse.

Г. Перекомпиляция
База может решить перекомпилировать запрос, если:

Ты добавил или удалил индекс.

Данных в таблице стало в 10 раз больше (статистика устарела).

Ты изменил структуру таблицы (ALTER TABLE).



Логический порядок выполнения SQL-запроса (то, как его видит «мозг» базы данных) сильно отличается от того, как мы его пишем глазами.

Представь, что база данных — это шеф-повар. Прежде чем подать блюдо (результат), он выполняет строгую последовательность действий: от выбора склада с продуктами до финального украшения тарелки.

Вот стандартный путь «сверху вниз», по которому идет проверка и объявление:

1. FROM (и JOIN) — «Где лежат данные?»
Это самый первый шаг. База определяет таблицу, к которой мы обращаемся. Если есть JOIN, она соединяет таблицы в одну огромную временную структуру.

Что происходит: Объявляются алиасы таблиц (например, Models as m). Теперь база знает, какие колонки ей доступны.

2. WHERE — «Какие строки выкинуть?»
База идет по строкам из шага 1 и проверяет их на соответствие условиям.

Важно: На этом этапе база знает только реальные имена колонок из таблиц. Она еще не видит того, что ты напишешь в SELECT.

3. GROUP BY — «Как сгруппировать?»
Оставшиеся после фильтрации строки разбиваются на группы по какому-то признаку (например, по цвету).

4. HAVING — «Какие группы выкинуть?»
Это как WHERE, но для групп. Здесь уже можно использовать агрегатные функции (AVG, SUM), потому что группы уже сформированы.

5. SELECT — «Что именно показать?»
Только на этом этапе база формирует финальный список колонок.

Здесь объявляются алиасы колонок (например, AS [Average Price]).

Выполняются вычисления и математика.

6. DISTINCT — «Убрать дубликаты?»
Если ты указал SELECT DISTINCT, база сравнивает полученные строки и удаляет идентичные.

7. ORDER BY — «Как отсортировать?»
Самый последний шаг перед выдачей.

Почему здесь работают алиасы? Потому что шаг SELECT уже прошел, и база «узнала» новые имена колонок. Поэтому ORDER BY [Average Price] сработает, а WHERE [Average Price] — нет.

8. LIMIT / OFFSET — «Сколько строк отдать?»
Финальная обрезка результата.
